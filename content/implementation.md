# Хранилище секретов — от дизайна к реализации

Документ-спутник к сводному дизайну. Домен считается закрытым; здесь — то, что
лежит между «домен готов» и «готово к реализации»: решения до кода, спецификация
адаптеров без развилок, раскладка crate’ов и порядок работ. Жанр тот же: решения с
мотивировкой, а не инструкция.

Снимок до редакции layout/CLI: `archive/secrets-vault-implementation-v4.md`.

**Канон портов и типов** — [`domain.rs`](https://github.com/skepsik/kip.design/blob/master/domain.rs)
(`HistoryPort`, `PackerPort`, `WorkTreePort`, `TablePersistence`, …). Здесь нет
второго, урезанного контракта портов. CLI и раскладка диска — [ux](./ux.md).

## 1. Решения, которые не примутся сами собой

### 1.1 Модель угроз локальной машины

Сводный дизайн защищает хранимый и синхронизируемый вид (граница защиты — дизайн 5.2в:
живое проникновение в разблокированную сессию — вне зоны; FDE и дисциплина окружения —
фон). На клиенте в открытом виде существуют рабочее дерево и клиентская таблица —
и таблица содержит ровно то, что дизайн прячет от наблюдателя репозитория: имена,
структуру, связи, сорта объектов.

**Решение: жизненный цикл таблицы = жизненному циклу дерева.** Таблица и дерево — одна
проекция и живут вместе: `open` создаёт обоих, `close` убирает обоих; свёрнутое
состояние оставляет на диске **только store** (`<vault>/.kip/vault`). Пока дерево
открыто, открытая таблица не добавляет атакующему ничего — плейнтекст лежит в папке
vault рядом с `.kip`; свёрнутое состояние не содержит ни таблицы, ни plaintext в
корне vault. Цена — холодный `open`: проход по метам дёшев, материализация тел —
честная стоимость. Персистентная таблица не заводится вовсе; если когда-либо
появится — обязана шифроваться, а `PlainHash` в ней быть ключёванным (HMAC под
ключом из VK).

**Layout (ux §2):** store root = `<vault>/.kip/vault` (git + россыпь + `vault-id`);
work tree = `<vault>` (parent of `.kip`). Materialize/cleanup/scan **не** трогают
`.kip/`. Маркер открытости, `sync-marker`, локальный **`.kip/ignore`** — файлы под
`.kip/` рядом с `vault/` (вне git). Общий **`.kipignore`** — в корне work tree,
уезжает в store обычным `save`. Work tree на обычном диске.

Пути (crate `vault-store`): константы `KIP_DIR` (`.kip`), `STORE_DIR` (`vault`),
`OPENED_MARKER` (`opened`), `SYNC_MARKER` (`sync-marker`); хелперы `kip_dir(vault)`,
`vault_store_path(vault)`.

**`VaultState` / `DiskVaultState`:** открытость — `is_opened` / `set_opened` (файл
`opened` под `.kip/`); sync — `sync_marker` / `set_sync_marker`. `DiskVaultState::open`
(без mkdir) / `ensure` (создаёт `.kip/`); `kip_dir()` / `root()` на адаптере.
Семантики `active_ram_root` / пути work tree вовне — нет.

**`StateError`:** `Io(std::io::Error)` для дисковых операций state; `Message` — не
единственный канал новых отказов.

Гигиена рабочего дерева (и таблицы — судьба общая):

- work tree = папка vault; при `close` — уборка plaintext с корня (кроме `.kip/`);
  `shred`/перезапись — с оговоркой про CoW/SSD;
- своп: отключён/зашифрован на уровне машины (проверять и предупреждать) либо
  признаём риск строчкой;
- редакторы оставляют бэкапы/undo — `close` подметает корень vault (не заходя в
  `.kip`), белый список мусора редакторов;
- VK — только в агенте с TTL, не в OS-keychain.
- **scan:** фильтр через crate **`ignore`** — `.kipignore` затем `.kip/ignore`
  (синтаксис gitignore, включая `!`); всегда skip `.kip/`. Не `.gitignore` store-репо.

### Rejected: встроенные app-дефолты ignore

Шаблоны приложений (например `.obsidian/`) в коде не зашивать — только явные
правила в ignore-файлах (ux §2.1).

### Rejected: work tree в tmpfs / отдельном пути

Внешний каталог (`/tmp/kip-vault/…`, tmpfs, `KIP_VAULT_RAM_ROOT`) — даже опцией.
Не кроссплатформенно; файл-менеджерный UX; mount на корень прячет store (ux §2).

### Rejected: store в `~/.kip/<id>`

Ломает перенос одной папкой и Windows UX (ux §2).

### 1.2 Конфликтная копия: конкретика

Правило домена «параллельная правка материализуется обеими версиями» при реализации
требует трёх уточнений:

- **Проигравшая версия получает новый `kNNN`** — это рождение узла-копии (новая мета +
  новое тело со старыми байтами проигравшего), с именем вида `имя.conflict-<суффикс>`
  рядом с победителем. Нельзя оставлять обе версии под одним `kNNN`: два устройства
  произвели бы разные объекты под одним именем, и конфликт воспроизвёлся бы на
  следующем же синке.
- **Победитель выбирается детерминированно** (например, лексикографически больший хэш
  версии), а не «локальная сторона»: иначе два устройства, одновременно разрешающие
  один конфликт, выберут разных победителей.
- **Исполнитель — устройство, делающее merge при pull**; результат уезжает обычным
  пушем, остальные получают готовое. Гонка двух одновременных разрешений безопасна
  только благодаря байтовому детерминизму: идентичные результаты сливаются чисто.
  Отсюда общее требование ко всем восстановительным операциям (воскрешение каталога,
  разрыв цикла, суффикс дубля, конфликтная копия): **никаких переупаковок там, где
  можно взять старые байты из истории** — переупаковка с нонсом ломает байтовый
  детерминизм. Новый нонс допустим только там, где рождается новый `kNNN` (узел-копия):
  для него имя уникально, коллизии имён нет; конфликт «двух разрешений» тогда
  вырождается в две копии-сироты, которые дедуплицируются правилом «копия с большим
  суффиксом удаляется, если байтово совпадает с меньшим».

### 1.3 Детекция изменений при свёртке сессии

Свёртка должна понять, какие файлы дерева правились. mtime ненадёжен (редакторы,
копирование, touch), сравнение через распаковку — противоречит стоимостной модели.
Решение: **хэш плейнтекста в таблице**, обновляется при развороте и свёртке; локально
это допустимо — таблица и так знает больше, чем хранилище (защита — решение 1.1:
жизненный цикл таблицы = дереву). Сравнение хэшей даёт точный список правок
за один проход по дереву без единой распаковки.

**`PlainHash`:** SHA-256 от байтов плейнтекста, 32 байта. Считается **вне домена**
(runtime / адаптер рабочего дерева при materialize/scan); в домене тип — только
носитель `[u8; 32]`, без зависимости от crypto-crate’ов.

Следствия того же решения:

- **переезд внутри дерева** детектируется как «знакомый хэш на новом пути» — надёжнее
  эвристик по inode и работает после копирования;
- **новый файл** = незнакомый хэш и незнакомый путь (с учётом правила полноты из
  дизайна: «новый» подтверждается по фактическому множеству объектов, не по кэшу);
- совпадение хэшей двух разных секретов легально (одинаковые пароли) — хэш это
  атрибут узла, не ключ таблицы.

### 1.4 Формат меты: версия схемы

В мету — целочисленное поле версии формата, с первого дня. Единственная строчка, о
которой все жалеют через год, если её нет. Правило эволюции: читаем все версии ≤
текущей, пишем всегда текущую; миграция просачивается лениво при естественных
переупаковках мет (тот же механизм, что у паддинга).

## 2. Спецификация адаптеров (механика без развилок)

### 2.1 git-адаптер

- Дельта: `git diff --name-status <метка>..HEAD` c принудительно выключенной
  rename-детекцией (`--no-renames`); статусы отображаются в доменные A/M/D один в один.
- `.gitattributes`: `* binary -diff -merge -text` — глушим текстовые эвристики,
  автоперевод строк и попытки содержательного merge на шифроблобах; конфликт
  modify/modify тогда гарантированно предъявляется, а не «разрешается».
- Метка последней синхронизации (`sync-marker`): хэш коммита, хранится локально под
  `.kip/` рядом с `vault/` (в git не коммитится; ux §2). Сдвигается только после
  успешного применения дельты, прохождения инвариантов **и материализации** (дизайн §6;
  `SyncMark` в `domain.rs`). Второй проход / материализация не прошли — метка стоит,
  дельта переприменима (идемпотентность разворота). HEAD store ≠ маркер: маркер —
  «kip учёл проекцию до этого коммита».
- Воскрешение/чтение истории: `git cat-file` / `checkout <hash> -- <имя>` — байты
  как были, без переупаковки (см. 1.2).
- Нормальная форма коммитов «один объект — один коммит», порядок: тело раньше меты,
  мета родителя раньше детей. Авторские таймстемпы нормализуются (квант до суток или
  фиксированное время) — они поле, а не факт. Джиттер/расписание пушей — опции поверх,
  с ценой в латентности синка.
- Исчезнувшая метка — штатная ситуация, не паника: метка не найдена в истории →
  случился purge → пересчитать дельту от ближайшего общего предка либо полным
  проходом (проход по метам дёшев). Обязательный тест-кейс адаптера.
- remote и push — ручные, необязательные операции: локальная конфигурация без origin
  легальна (дизайн 5.2б), адаптер не предполагает существование remote нигде;
  `git bundle` — штатный путь второй копии.

### 2.2 Упаковщик

- Ключевая иерархия (дизайн 5.2а): случайный vault key; объекты шифруются VK. Фраза
  оборачивает VK в слоте — объекте россыпи с именем, детерминированно выведенным из
  фразы (соль — **vault-id**: случайный, рождается при `init`, единственный
  нешифрованный объект репозитория, read-only навсегда — ни одна операция его не
  пишет; НЕ url, НЕ имя каталога, НЕ хэш коммита; дизайн 5.2а). Обёртка слота —
  **argon2id**
  (memory-hard; параметры — константы конфигурации, калиброванные на ~секунду
  интерактивного unlock), не итерированный SHA-S2K; при заведении фразы `init` предупреждает
  о словарных фразах — KDF курс меняет, энтропию не заменяет.
- **Формат блоба (wire, с первого дня):** `заголовок упаковщика || ciphertext`.
  Заголовок — фиксированный префикс до расшифровки: magic (4 байта `KIPV`),
  `pack_version` (u8), **`vk_epoch`** (u8). Запись по умолчанию:
  `pack_version = 1`, `vk_epoch = 1`. Ciphertext — полезная нагрузка адаптера
  (слот — обёртка ниже; мета и тело — seal под VK, дефолт: gpg batch).
  **`vk_epoch`** — поколение vault key: `1` при `init`, растёт **только** на
  `rotate-vk`; `passwd` его не меняет (VK тот же). Поле обязательно, чтобы позже
  не мигрировать формат. Чтение: нет magic → legacy (считать `vk_epoch = 1`) — на
  случай досрочных прототипов без заголовка.
- **Объект слота (раскладка на диске):** тот же wire, что у прочих блобов;
  ciphertext wire — обёртка VK:
  - VK — 32 случайных байта;
  - обёртка: `salt (16) || nonce (12) || AES-256-GCM(VK)` (в ciphertext — tag GCM);
  - ключ AES-256: **argon2id** от фразы, соль = `salt` из обёртки, выход 32 байта;
    прод-параметры (константы конфигурации, бюджет ~1s unlock): memory 65536 KiB,
    time cost 3, parallelism 4;
  - имя объекта слота: `SHA-256( vault-id_ascii || 0x00 || passphrase_utf8 )` →
    lowercase hex (64 символа); соль имени — открытый **vault-id** (16 случайных
    байт → lowercase hex, объект россыпи с именем `vault-id`).
- `unlock`: вычислить имя слота → прочитать → развернуть VK → держать на сессию
  (агент, явный TTL). Успешное развёртывание VK **и есть** проверка слота — отдельной
  подсистемы самопроверки не существует; сверка и починка копий слота (локальная ↔
  remote) — обязанность `fsck`, не unlock.
- `passwd` — цепочка с фиксированным порядком: записать новый слот → раундтрип-
  верификация (прочитать назад, развернуть VK новой фразой, сверить с VK в агенте) →
  удалить старый → **purge старого из истории** (обязательная часть семантики, дизайн
  5.2а; в тексте дизайна иногда «`passwd --purge`» — тот же обязательный purge, не
  опциональный режим). На уровне дельты это `D` + `A` (имя слота следует за фразой),
  два синглетона нормальной формы; обрыв цепочки в любой точке оставляет рабочий
  слот — покрывается тестом цепочки.
- Ротация VK — отдельная аварийная команда (**после MVP**, §2.6): полное
  перешифрование + отсечение истории + перечеканка слота под новый VK +
  `vk_epoch++`; в обычной жизни не вызывается (иерархия операций — дизайн 5.2а).
- Холодный старт начинается с поиска слота — единственный объект, который надо уметь
  найти до того, как есть таблица и ключи.
- Симметричный режим; тело — шифрование исходного файла байт-в-байт,
  мета — шифрование сериализованной записи. Никакой склейки.
- Паддинг до размерных корзин — политика упаковщика, включается флагом, просачивается
  лениво. Корзины фиксируются константами конфигурации, не вычисляются от содержимого.
- gpg-agent: фраза вводится раз на сессию; TTL агента — часть модели угроз локальной
  машины (1.1), выставляется явно, а не по умолчанию.
- Пустышки-chaff: рождаются упаковщиком как объекты легального формата; таблица
  помечает их мусором; машинерия дельты и merge-валидность их не различают — это
  тест на честность границы (если различают, граница протекла).

### 2.3 Таблица

Канон полей — `domain.rs` (`Table`, `Sort`, `NodeEntry`, `Meta`). Сорт объекта:
`мета` / `тело` / **`chaff`** (design §5.4 — открытый вопрос критерия распознавания;
машинерия дельты и merge chaff не выделяет — §2.2). Для мет в записи таблицы —
место (`parent`/`name`), ссылка на тело | ∅, опциональный `PlainHash` (детекция
правок, 1.3); **версия схемы** живёт в мете (`Meta.schema`, 1.4), не отдельным
полем строки таблицы. Обратный индекс «дети по родителю» — производный, в памяти.
Персистентность — по решению 1.1. Атомарность записи — `temp + rename`. Сверка имён
и самопочинка — design §5.3.

### 2.4 CLI-скелет (минимальный контур)

`init` · `open` · `save` · `close` / `close --discard` · `discard` · `status` ·
`clone` · `sync` · `fsck` · `passwd` · `rm` / `rm --cached` / `rm --purge` ·
`history` / `restore`. Правки секретов — обычные файловые операции в открытом
дереве (ux §4).

**`resolve_vault_path`:** резолв корня существующего vault (ux §2.2). Вход —
`Path` старта (явный аргумент CLI или cwd). Обход старта и родителей; находка —
каталог, у которого есть дочерний каталог `.kip`; возврат — этот каталог (work
tree / vault path). Нет находки / старт не каталог — типизированный отказ.
Симлинки: без обязательного полного `canonicalize`. Команды по существующему
vault (`open` / `save` / `close` / `sync` / `fsck` / `history` / `restore` /
`passwd` / `rm` / …) опираются на этот резолв. **`init` / `clone`** — нет (path
назначения свой).

Имя и поведение — опора для CLI и соседних модулей; не оставлять «на усмотрение».

**`init`:** подготовка `<path>` (по умолчанию `.`; создать папку при отсутствии;
отказ если уже `.kip` — `RuntimeError::VaultAlreadyExists`; отказ если `.git` в
корне path — `GitRepoExists`) → `git init` в `<path>/.kip/vault` → passphrase →
`seal_new_vault` → `VaultSession::open_initial` (маркер `opened`; **без** wipe
work tree). Фразу не читать до успешного prepare. Непустой корень с файлами —
штатный кейс (файлы = work tree). Отказа `PathNotEmpty` нет.

**`clone <url> [path]`:** `clone_vault_store` — `git clone` remote **в**
`<dest>/.kip/vault`; `DiskVaultState::ensure` (локальные маркеры с нуля, не из
remote). Dest по умолчанию — имя из URL (как у `git clone`). Отказ при уже
`.kip` / `.git` в корне (`VaultAlreadyExists` / `GitRepoExists`); непустой dest
без них — ок (как init). Провал `git clone` — убрать `.kip` для retry.
CLI: `clone_vault_at` + `CloneOptions { closed }` / `CloneError`. По умолчанию —
passphrase → `open_initial`; `--closed` — без open и без чтения фразы.

**`status`:** resume → сравнение work tree с baseline последнего save (PlainHash /
множество путей); вывод для человека; машинно — сам факт dirty (ненулевой exit или
стабильный код). Без index/staging.

**`discard`:** resume → rematerialize work tree из последнего сохранённого store;
baseline/table согласованы с store; vault остаётся открыт.

**`close` / `close --discard`:** по умолчанию resume → save → teardown plaintext;
`--discard` — resume → teardown без save.

**`rm` / `--cached` / `--purge`:** resume → preflight → (для `--purge` — confirm CLI)
→ изменение актуального графа + при необходимости `purge_from_history` → фиксация в
store (внутренний save затронутого). Путь — work tree; для `--cached`/`--purge` файл
на диске не обязателен (актуальный граф + история). После `--purge` при remote —
warn про `git push --force`. Отдельной команды `purge` нет.

**`fsck` (MVP, дымовой):** unlock по фразе + сверка store в `.kip/vault` (`vault-id`,
tracked-имена / мета↔тело, читаемость тел). **Без** materialize дерева. Отчёт —
`FsckReport`: `problems` / `notes`. Самопочинка remote-слота — вне MVP.

### 2.5 Бюджеты сложности мелочей

Строчка в дизайне не равна строчке в коде; для перечисленного ниже бюджет — потолок,
превышение которого означает, что реализация решает не ту задачу:

- **Предупреждение о словарных фразах в `init`** — проверка длины плюс вхождение в
  top-N словарь (текстовый файл). **Короткая** = короче **12** символов Unicode
  (скалярных значений). Никаких библиотек оценки энтропии, никакого zxcvbn.
- **Проверка слота при unlock** — ноль дополнительного кода: успех развёртывания VK и
  есть проверка. Сверка копий — только в `fsck`, и только как сравнение байтов двух
  объектов с заменой битого небитым.
- **`rm --purge`** — обёртка над `purge_from_history` порта, который уже оплачен
  `passwd`-ом, плюс подтверждающий диалог. Никакой собственной механики истории.

### 2.6 Следующие фичи упаковщика (после MVP)

Заголовок с `vk_epoch` закладывается в MVP (§2.2); ниже — поведение, которое
включается отдельно, без переделки домена и без обязательной миграции существующих
vault'ов (пока пользователь не запустил `rotate-vk`).

**`rotate-vk`** — команда CLI (дизайн 5.2а, ux §6.4): новый случайный VK, перепак
всех мет и тел с новым `vk_epoch`, отсечение истории, перечеканка слота, force-push
и переклон устройств — как после `passwd`. Единственный штатный момент полной
перешифровки хранилища.

**Синхронизация эпох между устройствами** — контракт агента при живой сессии (спящий
на одном устройстве, как merge-валидность):

- холодный `unlock`: объекта-слота под вычисленным именем нет → сброс агента,
  запрос актуальной фразы, без материализации;
- живой агент: при `pull`/чтении первый объект с `vk_epoch` выше локального → сброс
  агента;
- фолбэк: ошибка аутентификации при валидном локальном состоянии → сначала проверить
  эпоху/слот, потом порчу.

Окно до первого контакта с репой после ротации кодом не закрывается; в церемонии
`rotate-vk` — одна строка: разблокированные устройства без синка считать носителями
старого VK до ручной проверки.

### 2.7 Оркестрация UX → runtime

| UX-команда | Runtime |
| ---------- | ------- |
| `open` | (опц. pull при необходимости — см. sync) дельта / два прохода → decrypt → materialize **в папку vault** → метка; work tree = parent of `.kip` |
| `save` | scan (ignore-фильтр) → `plan_pack` → seal → запись блобов + `HistoryPort::commit` × N → update table |
| `close` | по умолчанию `save` + teardown plaintext с корня / таблицы (1.1); `--discard` — teardown без save; `.kip/` не трогать как store |
| `discard` | resume → rematerialize из последнего save; остаётся открыт |
| `status` | resume → dirty vs baseline последнего save |
| `clone` | `git clone` → `.kip/vault`; маркеры с нуля; по умолчанию `open`; `--closed` — без open |
| `sync` | **save → pull → apply → save**; затем **push**, если в прогоне не было `PresentedConflict`; иначе без push, сообщение со списком конфликтных путей, ненулевой exit CLI |
| `passwd` | unlock → `change_passphrase` → `commit_one` нового слота; без work tree / open / resume; при remote — warn про `git push --force` |
| `rm` / `--cached` / `--purge` | resume → preflight → (confirm на `--purge`) → untrack / optional disk delete / `purge_from_history` → фиксация в store |

Упаковка и коммиты **неделимы** внутри `save` (ux §5.1). Имена методов портов — как в
`domain.rs`; CLI-имена — ux.

**Merge при `open`/`sync`:** object-wise 3-way merge шифроблобов при расхождении с
remote. Параллельная правка → `PresentedConflict` → conflict copy
`имя.conflict-<суффикс>` (implementation §1.2 / design §4). Persist merge в store —
после успешного validate.

**Процессы CLI:** отдельные вызовы бинаря. Таблица между процессами не персистится.
Store = `<vault>/.kip/vault`; work tree = `<vault>`. Маркер открытости — под `.kip/`
(не абсолютный путь вовне). `resume`: vault открыт → пересобрать таблицу из store +
baseline-хэши из тел, не перезаписывая дерево без нужды. Холодный `open` —
`unlock` + materialize. Резолв корня vault — **`resolve_vault_path`** (ux §2.2 /
§2.4).

**`sync`:** вход в сессию (свёрнут: unlock+open; открыт: resume) → save → pull/merge →
apply/materialize → save → push только если конфликтов в этом прогоне не было.
Object-wise merge — тот же путь, что при apply после pull (kip#28).

**`history` / `restore`:** путь в work tree; `restore` пишет файл в дерево без reseal;
фиксация — `save`/`close`.

**`passwd` / `rm --purge`:** force-push после переписывания истории — вне обычного
`sync` (§2.2 / ux).

**Карта CLI → runtime** (имена функций — ориентир; при переименовании команд обновить
вместе с кодом):

| `kip` (ux) | CLI | Runtime |
| ---------- | --- | ------- |
| (резолв path) | `resolve_vault_path` | корень vault по ux §2.2; до `*_vault_at` команд по существующему vault |
| `init [path]` | `init_vault_at` | prepare → passphrase → seal → `open_initial` (§2.4) |
| `open` | `open_vault_at` | unlock + `open` (wipe + materialize; work tree = vault path) |
| `save` | `save_vault_at` | resume + save (бывш. pack) |
| `close` / `--discard` | `close_vault_at` | resume + close (default save) / teardown-only |
| `discard` | `discard_vault_at` | resume + rematerialize from last save |
| `status` | `status_vault_at` | resume + dirty vs baseline |
| `clone <url> [path]` | `clone_vault_at` + `CloneOptions` | `clone_vault_store` → маркеры; default `open_initial`; `--closed` — без open |
| `fsck` | `fsck_vault_at` | `fsck_vault` → `FsckReport` |
| `history <path>` | `history_vault_at` | resume + history |
| `restore <path>@<rev>` | `restore_vault_at` | resume + restore |
| `sync` | `sync_vault_at` | save→pull→apply→save→push\|stop-on-conflict |
| `passwd` | `passwd_vault_at` | `passwd_vault` |
| `rm` / `--cached` / `--purge` | `rm_vault_at` | resume → untrack / optional disk / optional purge |

**Ошибки runtime / CLI:** типизированные каналы.

- **`RuntimeError`:** `NotOpen` (нет маркера `opened` / нельзя `resume`);
  `AlreadyOpen` (повторный холодный open при уже открытом);
  `VaultAlreadyExists` (prepare/init/clone при уже имеющемся `.kip`);
  `GitRepoExists` (`.git` в корне path при prepare/clone). `PathNotEmpty` нет.
  Внешнего `ActiveRootMissing` / RAM-root path в ошибках нет.
- **`VaultSession::open_initial`:** первое открытие после seal (init) или после
  clone (default) — materialize/opened без cleanup существующих файлов work tree.
  Обычный `open` — с wipe.
- **`clone_vault_store`:** runtime-хелпер clone store в `.kip/vault` (см. §2.4).
- **`CloneError` / `CloneOptions`:** CLI-канал clone; `closed` = без open.
- **`ResolveVaultError`** (`vault-cli`, `resolve_vault_path`): `NotFound`,
  `StartNotDirectory`, `Io`. Обёртки команд — `LifecycleError::Resolve`,
  `SyncError::Resolve`, `FsckError::Resolve`, `HistoryError::Resolve`,
  `PasswdError::Resolve`, `PurgeError::Resolve` (`#[from]`).
- **`StateError`:** `Io` + при необходимости `Message`.
- `PassphraseError` — ux §6.1.

Дисковый адаптер дерева: `DiskWorkTree<S: BlobStore>`, `open(root, store)` —
`root` = vault path (work tree); accessor **`root()`** (не `ram_root`).
cleanup/materialize/scan пропускают `.kip/` структурно. Фильтр `.kipignore` /
`.kip/ignore` через crate `ignore` — P8.

## 3. Workspace (crate layout)

Репозиторий кода `kip` (бинарный продукт — `kip`):

```
kip/
  Cargo.toml              # workspace
  crates/
    vault-domain/         # чистый домен: граф, дельта, merge (без I/O)
    vault-ports/          # trait-порты и opaque-id по domain.rs
    vault-store/          # блобы в корне `.kip/vault`
    vault-git/            # git subprocess (история / дельта / commit)
    vault-crypto/         # упаковщик (адаптер PackerPort; дефолт — gpg batch)
    vault-runtime/        # склейка open/save/close/sync
    vault-cli/            # clap; бинарь `kip`
```

**Зависимости:**

```
vault-cli → vault-runtime, vault-store
vault-runtime → vault-domain, vault-store, vault-git, vault-crypto, vault-ports
vault-git, vault-crypto, vault-store → vault-ports
vault-domain → vault-ports (+ serde для меты)
```

`vault-cli` → `vault-store` напрямую: константы/`KIP_DIR` для `resolve_vault_path`.

`vault-domain` не зависит от store/git/crypto/runtime/cli и не импортирует
`std::fs` / `std::process` (gate агентов — в `.cursor/rules/ops.mdc`).

Физическое дробление адаптеров (store / git / crypto) — удобство crate’ов; **контракт**
для домена и runtime — порты из `domain.rs`, не отдельный MVP-скетч имён.

Намеренно без `git2` / Sequoia на MVP — subprocess системных `git` и упаковщика.

## 4. Порядок работ и тест-инвариант

Строить в таком порядке, и тесты — одновременно с ядром, не после:

1. **Ядро домена в памяти, без git и gpg вовсе**: узлы, таблица, применение дельты в
   два прохода, merge-валидность. Порты — интерфейсами по `domain.rs`, адаптеры —
   фейками (in-memory история). Граница из раздела 5 дизайна впервые окупается здесь:
   домен тестируем без единого вызова инструментов.
2. **Property-тест сходимости** — главный тест системы: два-три виртуальных устройства,
   случайный поток операций (создание, правка, mkdir/mv/rm, в т.ч. каталоги),
   произвольные точки sync/merge → после полного обмена проекции байтово совпадают,
   инварианты графа держатся, мультимножество тел сходится с учётом конфликтных копий.
   Сходимость восстановительных процедур (1.2) — его же цель. До подключения реальных
   адаптеров — на фейках; после git/упаковщика — тот же сценарий поверх них
   (медленнее допустимо).
3. **Адаптер git** (`HistoryPort` / tempfile-repo) — настоящая история; тот же
   property поверх реальных репозиториев.
4. **Упаковщик** (`PackerPort`: unlock, seal/open, change_passphrase, `open_count`) —
   ортогонален логике домена; wire `header || ciphertext`; fake и боевой адаптер —
   **одна** форма блоба. Ядро и domain-property остаются на fake; шифрование не должно
   менять смысл тестов сходимости, кроме стоимостных границ.
5. **CLI и гигиена дерева** (1.1) — поверх готового ядра.

Отдельный дымовой тест стоимостной модели: счётчик распаковок (`PackerPort::open_count`
/ эквивалент на fake); сценарии «переезд каталога с N потомками», «правка одного
секрета из N» — O(1) распаковок.

Фазы трекера (P1…P6) — чеклист эпиков в kip issues; этот § — порядок зависимостей
работ, не дублирует номера issue.

## Приложение. Чек-лист решений этого документа

- Локальная модель угроз: жизненный цикл таблицы = жизненному циклу дерева
  (свёрнутое — на диске только `<vault>/.kip/vault`; work tree = папка vault;
  при `close` — уборка plaintext; tmpfs/внешний RAM-root и store в `~/.kip/<id>` —
  Rejected §1.1); своп и TTL агента — явные строчки; VK — только в агенте; FDE — фон
  (дизайн 5.2в).
- Конфликтная копия: новый `kNNN`, детерминированный победитель, исполнитель — кто
  мёржит; все восстановительные операции — старыми байтами из истории, без переупаковок.
- Детекция правок: `PlainHash` = SHA-256 плейнтекста (считается вне домена) в таблице;
  переезд — знакомый хэш на новом пути; «новый» — по фактическому множеству объектов.
- Мета несёт версию схемы; читаем все ≤, пишем текущую, миграция ленивая.
- git: `--no-renames`, всё binary/-merge, метка сдвигается после инвариантов **и
  материализации**, применение дельты идемпотентно, нормальная форма коммитов с порядком
  «тело → мета → …», таймстемпы нормализованы; исчезнувшая метка = purge, пересчёт
  от общего предка — штатно и с тест-кейсом; remote/push — ручные и необязательные,
  `git bundle` — путь второй копии.
- Упаковщик: VK + слоты; соль имени слота — vault-id (случайный, при `init`,
  единственный открытый объект, read-only навсегда; переезд/переименование репы
  свободны; сигнатура формата принята); слот под argon2id (~секунда на unlock, `init` предупреждает
  о словарных фразах — короче 12 символов + top-N словарь, без библиотек); `passwd` = «новый →
  раундтрип-верификация → удаление → purge» (`D`+`A`), обрыв в любой точке оставляет
  рабочий слот — покрывается тестом цепочки; учётная данная одна — фраза; wire-формат
  блоба — заголовок (`pack_version`, `vk_epoch`) + ciphertext, с MVP `vk_epoch=1`;
  `rotate-vk` и синхронизация эпох — после MVP (§2.6); ротация VK — аварийная
  (перешифрование + отсечение истории + `vk_epoch++`);
  unlock сам есть проверка слота, сверка копий — в `fsck`; `kip rm` / `--cached`
  обратимы историей; `kip rm --purge` — явный выжиг для нератируемых секретов;
  scan — crate `ignore` + `.kipignore` / `.kip/ignore`; бюджеты сложности
  мелочей — 2.5; холодный старт начинается со слота.
- Порты — `domain.rs`; раскладка crate’ов — §3; порядок работ — §4.
- Порядок работ: ядро на фейках → property-тест сходимости → git → упаковщик → CLI;
  счётчик распаковок как регрессионный тест стоимостей.
