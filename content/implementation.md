# Хранилище секретов — от дизайна к реализации

Документ-спутник к сводному дизайну. Домен считается закрытым; здесь — то, что
лежит между «домен готов» и «готово к реализации»: три решения, которые надо принять
до кода, спецификация адаптеров без развилок и порядок работ. Жанр тот же: решения с
мотивировкой, а не инструкция.

---

## 1. Решения, которые не примутся сами собой

### 1.1 Модель угроз локальной машины

Сводный дизайн защищает хранимый и синхронизируемый вид (граница защиты — дизайн 5.2в:
живое проникновение в разблокированную сессию — вне зоны; FDE и дисциплина окружения —
фон). На клиенте в открытом виде существуют рабочее дерево и клиентская таблица —
и таблица содержит ровно то, что дизайн прячет от наблюдателя репозитория: имена,
структуру, связи, сорта объектов.

**Решение: жизненный цикл таблицы = жизненному циклу дерева.** Таблица и дерево — одна
проекция и живут вместе: разворот создаёт обоих, свёртка убирает обоих; свёрнутое
состояние оставляет на диске **только репозиторий**. Пока дерево развёрнуто, открытая
таблица не добавляет атакующему ничего — плейнтекст лежит рядом; свёрнутое состояние
не содержит ни того, ни другого. Цена — холодный разворот каждой сессии: проход по
метам дёшев, материализация тел — честная стоимость разворота при любом раскладе.
Персистентная таблица не заводится вовсе; если когда-либо появится (кэш между
сессиями) — она обязана шифроваться, а `PlainHash` в ней быть ключёванным (HMAC под
ключом из VK): открытый хэш короткого секрета — оракул для словарного перебора
конкретного пароля без всякой фразы.

Гигиена рабочего дерева (и таблицы — судьба общая):

- разворачивать в каталог с предсказуемым временем жизни: tmpfs/ramdisk, либо
  затирание при свёртке (`shred`/перезапись — с оговоркой, что на CoW/SSD затирание
  негарантированно; tmpfs честнее);
- своп: либо отключён/зашифрован на уровне машины (проверять и предупреждать), либо
  признаём риск строчкой;
- редакторы оставляют бэкапы/undo-файлы (`*~`, `.swp`) — свёртка обязана подметать
  каталог целиком, а не только известные ей файлы; неизвестный файл в дереве — это
  либо новый секрет, либо мусор редактора, различать по явному правилу (белый список
  паттернов мусора), в сомнении — спрашивать;
- VK — только в агенте с TTL, не в OS-keychain (keychain разблокирован вместе с
  логин-сессией, то есть вместе со всем остальным).

### 1.2 Конфликтная копия: конкретика

Правило домена «параллельная правка материализуется обеими версиями» при реализации
требует трёх уточнений:

- **Проигравшая версия получает новый `kNNN`** — это рождение узла-копии (новая мета +
  новое тело со старыми байтами проигравшего), с именем вида `имя.conflict-<суффикс>`
  рядом с победителем. Нельзя оставлять обе версии под одним `kNNN`: два устройства
  произвели бы разные объекты под одним именем, и конфликт воспроизвёлся бы на
  следующем же синке.
- **Победитель выбирается детерминированно** (например, лексикографически больший хэш
  версии), а не «локальная сторона»: иначе два устройства, одновременно разрешающие
  один конфликт, выберут разных победителей.
- **Исполнитель — устройство, делающее merge при pull**; результат уезжает обычным
  пушем, остальные получают готовое. Гонка двух одновременных разрешений безопасна
  только благодаря байтовому детерминизму: идентичные результаты сливаются чисто.
  Отсюда общее требование ко всем восстановительным операциям (воскрешение каталога,
  разрыв цикла, суффикс дубля, конфликтная копия): **никаких переупаковок там, где
  можно взять старые байты из истории** — переупаковка с нонсом ломает байтовый
  детерминизм. Новый нонс допустим только там, где рождается новый `kNNN` (узел-копия):
  для него имя уникально, коллизии имён нет; конфликт «двух разрешений» тогда
  вырождается в две копии-сироты, которые дедуплицируются правилом «копия с большим
  суффиксом удаляется, если байтово совпадает с меньшим».

### 1.3 Детекция изменений при свёртке сессии

Свёртка должна понять, какие файлы дерева правились. mtime ненадёжен (редакторы,
копирование, touch), сравнение через распаковку — противоречит стоимостной модели.
Решение: **хэш плейнтекста в таблице**, обновляется при развороте и свёртке; локально
это допустимо — таблица и так знает больше, чем хранилище (а её защита — вопрос 1.1,
и выбор там варианта 2/3 закрывает и это). Сравнение хэшей даёт точный список правок
за один проход по дереву без единой распаковки.

Следствия того же решения:

- **переезд внутри дерева** детектируется как «знакомый хэш на новом пути» — надёжнее
  эвристик по inode и работает после копирования;
- **новый файл** = незнакомый хэш и незнакомый путь (с учётом правила полноты из
  дизайна: «новый» подтверждается по фактическому множеству объектов, не по кэшу);
- совпадение хэшей двух разных секретов легально (одинаковые пароли) — хэш это
  атрибут узла, не ключ таблицы.

### 1.4 Формат меты: версия схемы

В мету — целочисленное поле версии формата, с первого дня. Единственная строчка, о
которой все жалеют через год, если её нет. Правило эволюции: читаем все версии ≤
текущей, пишем всегда текущую; миграция просачивается лениво при естественных
переупаковках мет (тот же механизм, что у паддинга).

## 2. Спецификация адаптеров (механика без развилок)

### 2.1 git-адаптер

- Дельта: `git diff --name-status <метка>..HEAD` c принудительно выключенной
  rename-детекцией (`--no-renames`); статусы отображаются в доменные A/M/D один в один.
- `.gitattributes`: `* binary -diff -merge -text` — глушим текстовые эвристики,
  автоперевод строк и попытки содержательного merge на шифроблобах; конфликт
  modify/modify тогда гарантированно предъявляется, а не «разрешается».
- Метка последней синхронизации: хэш коммита, хранится локально рядом с таблицей
  (в git не коммитится). Сдвигается только после успешного применения дельты и
  прохождения инвариантов — второй проход не прошёл, метка стоит, дельта
  переприменима (идемпотентность применения — требование к развороту).
- Воскрешение/чтение истории: `git cat-file` / `checkout <hash> -- <имя>` — байты
  как были, без переупаковки (см. 1.2).
- Нормальная форма коммитов «один объект — один коммит», порядок: тело раньше меты,
  мета родителя раньше детей. Авторские таймстемпы нормализуются (квант до суток или
  фиксированное время) — они поле, а не факт. Джиттер/расписание пушей — опции поверх,
  с ценой в латентности синка.
- Исчезнувшая метка — штатная ситуация, не паника: метка не найдена в истории →
  случился purge → пересчитать дельту от ближайшего общего предка либо полным
  проходом (проход по метам дёшев). Обязательный тест-кейс адаптера.
- remote и push — ручные, необязательные операции: локальная конфигурация без origin
  легальна (дизайн 5.2б), адаптер не предполагает существование remote нигде;
  `git bundle` — штатный путь второй копии.

### 2.2 Упаковщик (gpg)

- Ключевая иерархия (дизайн 5.2а): случайный vault key; объекты шифруются VK. Фраза
  оборачивает VK в слоте — объекте россыпи с именем, детерминированно выведенным из
  фразы (соль — **vault-id**: случайный, рождается при `init`, единственный
  нешифрованный объект репозитория, read-only навсегда — ни одна операция его не
  пишет; НЕ url, НЕ имя каталога, НЕ хэш коммита; дизайн 5.2а). Обёртка слота —
  **argon2id**
  (memory-hard; параметры — константы конфигурации, калиброванные на ~секунду
  интерактивного unlock), не gpg-шный S2K; при заведении фразы `init` предупреждает
  о словарных фразах — KDF курс меняет, энтропию не заменяет.
- **Формат блоба (wire, с первого дня):** `заголовок упаковщика || ciphertext`.
  Заголовок — фиксированный префикс до расшифровки: magic (4 байта), `pack_version`
  (u8), **`vk_epoch`** (u8). Ciphertext — симметричный вывод адаптера (gpg batch).
  Слот, мета и тело — одинаковая обёртка. **`vk_epoch`** — поколение vault key:
  `1` при `init`, растёт **только** на `rotate-vk`; `passwd` его не меняет (VK тот
  же). MVP пишет все объекты с `vk_epoch = 1`; поле обязательно, чтобы позже не
  мигрировать формат. Чтение: нет magic → legacy (считать `vk_epoch = 1`) — на случай
  досрочных прототипов без заголовка.
- `unlock`: вычислить имя слота → прочитать → развернуть VK → держать на сессию
  (агент, явный TTL). Успешное развёртывание VK **и есть** проверка слота — отдельной
  подсистемы самопроверки не существует; сверка и починка копий слота (локальная ↔
  remote) — обязанность `fsck`, не unlock.
- `passwd` — цепочка с фиксированным порядком: записать новый слот → раундтрип-
  верификация (прочитать назад, развернуть VK новой фразой, сверить с VK в агенте) →
  удалить старый → **purge старого из истории** (обязательная часть семантики, дизайн
  5.2а). На уровне дельты это `D` + `A` (имя слота следует за фразой), два синглетона
  нормальной формы; обрыв цепочки в любой точке оставляет рабочий слот — покрывается
  тестом цепочки.
- Ротация VK — отдельная аварийная команда (**после MVP**, §2.6): полное
  перешифрование + отсечение истории + перечеканка слота под новый VK +
  `vk_epoch++`; в обычной жизни не вызывается (иерархия операций — дизайн 5.2а).
- Холодный старт начинается с поиска слота — единственный объект, который надо уметь
  найти до того, как есть таблица и ключи.
- Симметричный режим; тело — шифрование исходного файла байт-в-байт,
  мета — шифрование сериализованной записи. Никакой склейки.
- Паддинг до размерных корзин — политика упаковщика, включается флагом, просачивается
  лениво. Корзины фиксируются константами конфигурации, не вычисляются от содержимого.
- gpg-agent: фраза вводится раз на сессию; TTL агента — часть модели угроз локальной
  машины (1.1), выставляется явно, а не по умолчанию.
- Пустышки-chaff: рождаются упаковщиком как объекты легального формата; таблица
  помечает их мусором; машинерия дельты и merge-валидность их не различают — это
  тест на честность границы (если различают, граница протекла).

### 2.3 Таблица

Формат записи: `имя объекта → сорт (мета/тело)`; для мет дополнительно
`kNNN → (имя, родитель, ссылка на тело | ∅, хэш плейнтекста, версия схемы)`; обратный
индекс «дети по родителю» — производный от таблицы, строится в памяти. Персистентность
— по решению 1.1. Атомарность записи — `temp + rename`, как в дизайне. Сверка и
самопочинка — по разделу 5.3 дизайна, без изменений.

### 2.4 CLI-скелет (минимальный контур)

`init` · `unfold` (разворот: pull → дельта → два прохода → материализация → метка) ·
`fold` (свёртка: скан дерева по хэшам → упаковка изменённого → нормальная форма
коммитов → уборка дерева) · `fsck` (сверка имён, починка таблицы, отчёт о
сиротах/дублях; сверка и починка копий слота локальная ↔ remote) ·
`passwd` (цепочка «новый → верификация → удаление → purge»; 2.2) ·
`purge <путь>` (отдельная команда: вычищение истории тел умершего узла для
нератируемого секрета; обычный `rm` в дереве всегда обратим — инвариант «нет
невосстановимых ошибок», дизайн 5.2а) ·
`history <путь>` / `restore <путь>@<ревизия>`. Всё остальное —
обычные файловые операции в развёрнутом дереве, чем дизайн и силён.

### 2.5 Бюджеты сложности мелочей

Строчка в дизайне не равна строчке в коде; для перечисленного ниже бюджет — потолок,
превышение которого означает, что реализация решает не ту задачу:

- **Предупреждение о словарных фразах в `init`** — проверка длины плюс вхождение в
  top-N словарь (текстовый файл). Никаких библиотек оценки энтропии, никакого zxcvbn.
- **Проверка слота при unlock** — ноль дополнительного кода: успех развёртывания VK и
  есть проверка. Сверка копий — только в `fsck`, и только как сравнение байтов двух
  объектов с заменой битого небитым.
- **`purge`** — обёртка над `purge_from_history` порта, который уже оплачен
  `passwd`-ом, плюс подтверждающий диалог. Никакой собственной механики истории.

### 2.6 Следующие фичи упаковщика (после MVP)

Заголовок с `vk_epoch` закладывается в MVP (§2.2); ниже — поведение, которое
включается отдельно, без переделки домена и без обязательной миграции существующих
vault'ов (пока пользователь не запустил `rotate-vk`).

**`rotate-vk`** — команда CLI (дизайн 5.2а, ux §6.4): новый случайный VK, перепак
всех мет и тел с новым `vk_epoch`, отсечение истории, перечеканка слота, force-push
и переклон устройств — как после `passwd`. Единственный штатный момент полной
перешифровки хранилища.

**Синхронизация эпох между устройствами** — контракт агента при живой сессии (спящий
на одном устройстве, как merge-валидность):

- холодный `unlock`: объекта-слота под вычисленным именем нет → сброс агента,
  запрос актуальной фразы, без материализации;
- живой агент: при `pull`/чтении первый объект с `vk_epoch` выше локального → сброс
  агента;
- фолбэк: ошибка аутентификации при валидном локальном состоянии → сначала проверить
  эпоху/слот, потом порчу.

Окно до первого контакта с репой после ротации кодом не закрывается; в церемонии
`rotate-vk` — одна строка: разблокированные устройства без синка считать носителями
старого VK до ручной проверки.

## 3. Порядок работ и тест-инвариант

Строить в таком порядке, и тесты — одновременно с ядром, не после:

1. **Ядро домена в памяти, без git и gpg вовсе**: узлы, таблица, применение дельты в
   два прохода, merge-валидность. Порты — интерфейсами, адаптеры — фейками
   (in-memory «репозиторий» с историей). Граница из раздела 5 дизайна впервые
   окупается здесь: домен тестируем без единого вызова инструментов.
2. **Property-тест сходимости** — главный тест системы, дешёвый благодаря детерминизму
   правил: два-три виртуальных устройства, случайный поток операций (создание, правка,
   переезд, удаление, включая каталоги), произвольные точки синка и merge → после
   полного обмена **проекции байтово совпадают** на всех устройствах, инварианты графа
   держатся, ни один секрет не потерян (мультимножество тел сходится с учётом
   конфликтных копий). Именно генератор найдёт кейсы merge-валидности, которые не
   придумались за время проектирования; сходимость восстановительных процедур (1.2) —
   его же прямая цель.
3. **Адаптер git** — подключить настоящую историю, прогнать тот же property-тест
   поверх реальных репозиториев (медленнее, реже, в CI — ночной прогон).
4. **Упаковщик gpg** — последним: он ортогонален всей логике, ядро и тесты гоняются
   на плейнтексте; шифрование не должно менять ни один тест, кроме стоимостных.
5. **CLI и гигиена дерева** (1.1) — поверх готового ядра.

Отдельный дымовой тест на честность стоимостной модели: счётчик распаковок в фейковом
упаковщике; сценарии «переезд каталога с N потомками», «правка одного секрета из N»
обязаны показывать O(1) распаковок — регресс здесь означает, что где-то протёк полный
путь или лишняя классификация.

## Приложение. Чек-лист решений этого документа

- Локальная модель угроз: жизненный цикл таблицы = жизненному циклу дерева
  (свёрнутое состояние — на диске только репозиторий; персистентной таблицы нет,
  а если появится — шифрованная, с ключёванным `PlainHash`); дерево — tmpfs либо
  полная уборка каталога при свёртке; своп и TTL агента — явные строчки; VK — только
  в агенте, не в keychain; живое проникновение в разблокированную сессию — вне зоны,
  FDE — фон (дизайн 5.2в).
- Конфликтная копия: новый `kNNN`, детерминированный победитель, исполнитель — кто
  мёржит; все восстановительные операции — старыми байтами из истории, без переупаковок.
- Детекция правок: хэш плейнтекста в таблице; переезд — знакомый хэш на новом пути;
  «новый» — по фактическому множеству объектов.
- Мета несёт версию схемы; читаем все ≤, пишем текущую, миграция ленивая.
- git: `--no-renames`, всё binary/-merge, метка сдвигается после инвариантов,
  применение дельты идемпотентно, нормальная форма коммитов с порядком
  «тело → мета → …», таймстемпы нормализованы; исчезнувшая метка = purge, пересчёт
  от общего предка — штатно и с тест-кейсом; remote/push — ручные и необязательные,
  `git bundle` — путь второй копии.
- Упаковщик: VK + слоты; соль имени слота — vault-id (случайный, при `init`,
  единственный открытый объект, read-only навсегда; переезд/переименование репы
  свободны; сигнатура формата принята); слот под argon2id (~секунда на unlock, `init` предупреждает
  о словарных фразах — длина + top-N словарь, без библиотек); `passwd` = «новый →
  раундтрип-верификация → удаление → purge» (`D`+`A`), обрыв в любой точке оставляет
  рабочий слот — покрывается тестом цепочки; учётная данная одна — фраза; wire-формат
  блоба — заголовок (`pack_version`, `vk_epoch`) + ciphertext, с MVP `vk_epoch=1`;
  `rotate-vk` и синхронизация эпох — после MVP (§2.6); ротация VK — аварийная
  (перешифрование + отсечение истории + `vk_epoch++`);
  unlock сам есть проверка слота, сверка копий — в `fsck`; `rm` всегда обратим,
  `purge <путь>` — отдельная команда для нератируемых секретов; бюджеты сложности
  мелочей — 2.5; холодный старт начинается со слота.
- Порядок работ: ядро на фейках → property-тест сходимости → git → gpg → CLI;
  счётчик распаковок как регрессионный тест стоимостей.
