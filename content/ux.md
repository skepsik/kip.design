# Хранилище секретов — пользовательский опыт

Документ-спутник к сводному дизайну и implementation. Фиксирует, как система
**выглядит и ощущается** для пользователя. Ключи и слот — design §5.2а; адаптеры —
implementation.

Снимок до редакции layout/CLI: `archive/secrets-vault-ux-v4.md`.

---

## 1. Ментальная модель

### 1.1. Два слоя

| Слой | Где | Кто задаёт структуру |
|------|-----|----------------------|
| **Дерево файлов** | папка vault (пока открыта) | **Пользователь** — любые имена и вложенность |
| **Хранилище в git** | `vault/.kip/vault/` | **Система** — непрозрачные случайные имена |

Источник правды — зашифрованные объекты в git. Именованное дерево в git не входит:
его воспроизводят из объектов и графа (`open`). Пока vault открыт, дерево лежит на
диске в папке vault (файл-менеджер, редакторы).

Типичный режим на основной машине: vault **долго открыт**. Kip — про синк через remote
и скрытую структуру store; локальная защита живого дерева — FDE / ОС (design §5.2в).

### 1.2. Открытое состояние

Пока хранилище **открыто**, одновременно живут:

- **рабочее дерево** — файлы и папки в папке vault (рядом с `.kip/`);
- **таблица** — граф узлов (родитель, имя, ссылки, хэши / `PlainHash`); на диске
  как **`.kip/table`** (вне store/git), пока стоит маркер открытости.

Свёрнутое состояние — только store в `.kip/vault` (нет plaintext в корне, нет
`.kip/table`; implementation §1.1). Полные пути в таблице не хранятся — вычисляются
из графа.

Правки в дереве сами таблицу не обновляют. Связка «файл ↔ узел» — на **`save`** или
**`close`**. До `save` изменения только в файлах; после reboot без `save` —
незафиксированные правки потеряны при следующем `open` (перезапись из store).
Кэш `.kip/table` после аварийного обрыва (reboot при open) либо согласован с
последним `save`/`open`, либо при порче/отсутствии пересобирается полным проходом.

Понятие **«сессия»** в CLI и документации не используется.

### 1.3. Команды в жизни пользователя

```
init     →  .kip/vault + слот; папка сразу открыта
работа   →  обычные операции в папке vault
save     →  упаковка + локальные коммиты в .kip/vault; файлы остаются
status   →  dirty относительно последнего save
discard  →  work tree = последнее сохранённое; vault остаётся открыт
close    →  save + убрать plaintext с корня; `--discard` — без save
open     →  снова материализовать секреты в папку
sync     →  save → pull → apply → save → push (если не было конфликтов)
clone    →  с remote; по умолчанию сразу open
rm       →  убрать из актуального (+ опц. диск / выжиг истории)
```

**Одна фраза для README:** секреты — обычная папка; шифр и git — в `.kip/vault`.
Открыл — работаешь в файл-менеджере; `save` фиксирует; `sync` — с remote.

## 2. Структура на диске

```
secrets-vault/                 # work tree
  passwords/…
  .kipignore                   # общий ignore → в store через save
  .kip/
      vault/                   # git-репозиторий = store (non-bare)
          .git/
          vault-id
          a7f3c9e2…            # шифроблоб
          …
      ignore                   # локальный ignore (не в git store)
      sync-marker              # локальный курсор kip
      opened                   # флаг «открыт»
      config                   # опционально
```

**Свёрнуто:** в корне только `.kip/`.  
**Открыто:** `.kip/` + обычные файлы/каталоги секретов (+ `.kipignore`, если есть в store
или создан локально до `save`).

Локальные файлы под `.kip/` (кроме содержимого `vault/`) создаёт kip; в git store не
входят. Work tree = родитель `.kip` — путь к дереву нигде абсолютным не хранится.

`cp -a` / `mv` всей папки на любую машину сохраняет store, маркеры и plaintext (если
был открыт).

### 2.1. Ignore

Два слоя (синтаксис как у gitignore, включая `!`):

| Файл | Область | В store |
|------|---------|---------|
| **`.kipignore`** | политика vault; корень work tree | да, обычным `save` |
| **`.kip/ignore`** | только эта машина | нет; переживает `close` |

Наложение: сначала `.kipignore`, затем `.kip/ignore`. При scan всегда пропускается
`.kip/` (структурно, не через ignore-файл).

Локальный `!` может вернуть путь, который общий слой игнорирует: на этой машине файл
попадёт в store; после sync/clone на другой машине (только общий ignore) файл
появится из store — как `git add -f`.

Исключения — только явные правила в этих файлах.

### 2.2. Путь к vault (`resolve_vault_path`)

Команды по **существующему** vault резолвят корень через **`resolve_vault_path`**
(implementation §2.4).

Поведение:

1. Вход: путь-старт — явный аргумент команды или, если его нет, cwd.
2. Старт должен быть существующим каталогом (иначе отказ).
3. Обход: сам старт, затем родители (`Path::parent`), пока есть родитель.
4. Находка: в каталоге есть дочерний элемент `.kip`, и это **каталог**. Корень
   vault — этот родительский каталог (work tree).
5. До корня ФС находки нет — отказ (vault не найден).
6. Симлинки: без обязательного `canonicalize` всего пути; обход и проверка
   `.kip` — по пути, который даёт ОС / `current_dir`.

**`init` / `clone`** этот резолв для поиска существующего vault **не** используют:
у них свой path назначения (создание).

### Rejected: встроенные app-дефолты ignore

Зашитые шаблоны вроде `.obsidian/` — нет. Политика ignore только в `.kipignore` /
`.kip/ignore`.

### Rejected: внешний work tree / tmpfs

Work tree во внешнем каталоге (`/tmp/kip-vault/…`, tmpfs, env вроде
`KIP_VAULT_RAM_ROOT`) — даже опцией. Не кроссплатформенно; стандартная работа —
файл-менеджер по папке vault; mount tmpfs на корень прячет store.

### Rejected: store в `~/.kip/<id>`

Ломает «одна папка на флешку» и доступность пути на Windows.

Пользователь не редактирует шифроблобы, `vault-id` и служебное под `.kip/` вручную.
Обычный `git` в корне vault без `-C .kip/vault` репозиторий не видит.

## 3. Имена и идентичность

### 3.1. Дерево (пользователь)

Полная свобода имён и вложенности. Имя `.kip` зарезервировано.

### 3.2. Объекты в git (система)

- **мета** — файл в корне `.kip/vault` с именем = id узла;
- **тело** — отдельный файл со случайным именем, ссылка в мете;
- **слот** — blob с обёрнутым vault key; имя из фразы и `vault-id`.

## 4. Команды CLI (MVP)

| Команда | Назначение |
|---------|------------|
| `kip init [path]` | По умолчанию `.`; `.kip/vault` + seal; сразу открыт. Основной кейс — уже существующая папка с файлами |
| `kip open` | Материализовать store в корень vault |
| `kip save` | Скан дерева → шифр + локальные коммиты; файлы остаются |
| `kip close` | По умолчанию: `save` + убрать plaintext с корня. `--discard` — убрать plaintext без `save` |
| `kip discard` | Пересобрать work tree из последнего сохранённого; vault остаётся открыт |
| `kip status` | Work tree ↔ последнее сохранённое; человек и машина (наличие изменений) |
| `kip clone <url> [path]` | Как `git clone` в `.kip/vault`; маркеры с нуля; по умолчанию `open`; `--closed` — свёрнут |
| `kip sync` | save → pull → apply → save → push, если не было конфликтных копий; иначе без push + сообщение со списком путей; ненулевой exit |
| `kip passwd` | Смена фразы; purge старого слота из истории |
| `kip rm <путь>` | Удалить с диска + убрать из актуального store (история тел сохраняется) |
| `kip rm --cached <путь>` | Оставить на диске; убрать из актуального store; история сохраняется |
| `kip rm --purge <путь>` | Оставить на диске; убрать из актуального + выжечь историю тел (design §5.2а); при remote — force-push |
| `kip fsck` | Сверка store (без materialize дерева) |
| `kip history <путь>` | Ревизии тела секрета (путь в work tree) |
| `kip restore <путь>@<rev>` | Подмена файла в дереве из истории; фиксация — `save`/`close` |

Путь к vault: **`resolve_vault_path`** (ux §2.2) — явный старт или cwd, обход
вверх до каталога с `.kip/`. Пути `history` / `restore` / `rm` — в
plaintext-дереве; для `--cached` / `--purge` файл на диске не обязателен (поиск
по актуальному графу и истории). Все варианты `rm` сами фиксируют изменение в
store. `kip rm` и затем `kip rm --purge` по тому же пути — валидно; после
`--purge` следующий `save` при живом файле на диске рождает новый узел.

**Remote:** `git -C .kip/vault remote …`. Отдача на remote — через `sync` (с push при
успехе без конфликтов). Голого push в CLI нет. Force-push после `passwd` /
`rm --purge` — отдельная церемония.

**За рамками MVP:** `rotate-vk` и синхронизация эпох (implementation §2.6); FUSE; TUI
конфликтов; chaff по умолчанию.

Правки секретов — обычные операции в папке vault. `rm` в файл-менеджере + `save` —
эквивалент духа `kip rm` без флагов.

## 5. `save`, `close`, `sync`

### 5.1. Упаковка и коммиты — неделимо

**`save`** (и фаза сохранения в **`close`**) всегда:

1. скан рабочего дерева и сверка с таблицей;
2. шифрование и запись изменённых блобов в `.kip/vault`;
3. автоматическая серия git-коммитов (один объект — один коммит; порядок: тело →
   мета, родитель → дети — design §5.4).

**`close`:** по умолчанию после фазы сохранения — убрать plaintext с корня vault
(`.kip/` остаётся). **`close --discard`:** та же уборка plaintext, без фазы
сохранения (локальные незафиксированные правки не попадают в store).

**`discard`:** пересобрать work tree из последнего сохранённого store; vault остаётся
открыт. Эквивалент по смыслу «сбросить dirty к baseline», без teardown.

### 5.2. `sync`

Цепочка: **save → pull → apply → save**, затем **push**, если в этом прогоне не
появились конфликтные копии. Если появились — push не выполняется; CLI сообщает, что
синк неполный, push не сделан, и печатает список конфликтных путей; ненулевой exit.
Повторный `sync` после правок снова проходит цепочку и при отсутствии новых конфликтов
делает push.

Конфликт: победитель на исходном пути; проигравшая версия рядом
(`имя.conflict-<суффикс>`). Выбор вручную в дереве, затем `save` / `sync`.

## 6. Фраза и ключи

### 6.1. Passphrase

Источники (по приоритету):

1. **Файл** — `KIP_VAULT_PASSPHRASE_FILE`; права `0600`.
2. **Переменная** `KIP_VAULT_PASSPHRASE`.
3. **Интерактивный ввод**.
4. **gpg-agent** — фраза и VK на TTL; не OS-keychain.

Файл с фразой не в репозитории vault.

Отказы (`PassphraseError`): пустая фраза; env не UTF-8; ошибка чтения файла /
интерактивного ввода / I/O.

**Vault-id** — открытый id в `.kip/vault`; вместе с фразой даёт имя слота.

### 6.2. Принцип слепка

Клон `.kip/vault` — слепок момента. Фраза эпохи слепка вскрывает его навсегда.
`passwd` и ротация VK управляют только будущим доступом.

### 6.3. Смена фразы (`passwd`)

`passwd` переписывает историю слота (purge) и при remote требует `git push --force` —
отдельная церемония, не обычный `sync`. CLI предупреждает после успешной команды
(implementation §2.7).

### 6.4. Ротация vault key (`rotate-vk`, аварийно)

После MVP (implementation §2.6). Полное перешифрование + отсечение истории.

## 7. Типичные сценарии

### 7.1. Первая настройка

```bash
cd ~/Documents/secrets   # уже есть файлы — или пустая папка
kip init
# правки в файл-менеджере
kip save
git -C .kip/vault remote add origin …
kip sync                 # push, если remote пустой / без конфликтов
```

### 7.2. Одна машина

```bash
# vault обычно уже открыт
# правки…
kip save
kip sync                 # когда нужно с remote
kip close                # редко
```

### 7.3. Второе устройство

```bash
kip clone git@…:secrets.git ~/secrets
# по умолчанию сразу open
```

### 7.4. История и откат

```bash
kip history keys/api.key
kip restore keys/api.key@abc1234
kip save
```

### 7.5. Компрометация

«Утекла фраза, слепок ещё нет» → `kip passwd` (+ force-push).

«Утекла пара слепок + фраза» → `kip rotate-vk` (после MVP); секреты — у эмитентов.

### 7.6. Конфликты при sync

`kip sync` → конфликтные копии в дереве → сообщение без push → правки → `kip sync`.

### 7.7. Убрать из vault / выжечь историю

```bash
kip rm keys/old.key              # диск + актуальное; история жива
kip rm --cached notes/draft.md   # только перестать трекать
kip rm --purge keys/leaked.key   # выжечь историю (+ force-push при remote)
```

### 7.8. Status

```bash
kip status                       # dirty относительно последнего save
```

### 7.9. Сброс локальных правок

```bash
kip discard                      # дерево = последнее save; остаётся открыт
kip close --discard              # свернуть без упаковки dirty
```

## 8. Безопасность (UX)

| Аспект | Поведение |
|--------|-----------|
| Рабочее дерево | папка vault на диске; после `close` — только `.kip/` (store; без plaintext) |
| Таблица | `.kip/table` на время open; после `close` — нет |
| VK / агент | gpg-agent с TTL; после `close` — сброс |
| Своп | Предупреждение при `open` / `clone` с open |
| Модель угроз | Наблюдатель git/remote; локальная машина доверенная |

---

## 9. Что пользователь не делает

- Не трогает шифроблобы и `vault-id` внутри `.kip/vault`.
- Не коммитит секреты через `git` вручную в store.
- Не кладёт plaintext внутрь `.kip/vault`.
- Не использует термин «сессия».

## 10. MVP

`init`, `open`, `save`, `close` (`--discard`), `discard`, `status`, `clone`, `sync`,
`passwd`, `fsck`, `history`, `restore`, `rm` (`--cached` / `--purge`); store в
`.kip/vault`; work tree = папка vault; passphrase из файла; `.kipignore` /
`.kip/ignore`.

**За рамками MVP:** `rotate-vk`; синхронизация эпох (§2.6); FUSE; TUI конфликтов;
chaff по умолчанию.

## Приложение. Сводка

- Дерево — папка vault (пока открыто); таблица — `.kip/table` на время open;
  свёрнуто — store в `.kip/vault` (без `table` / plaintext).
- **`save`** = упаковка + локальные коммиты; **`close`** = `save` + teardown;
  **`close --discard`** = teardown без save; **`discard`** = rematerialize, открыт.
- **`sync`** = save → pull → apply → save → push без конфликтов; при конфликтах — без push + список путей.
- **`clone`** с remote; по умолчанию open; `--closed` опционален.
- Одна фраза, один слот; объекты шифруются VK.
- **Ignore:** `.kipignore` (общий) + `.kip/ignore` (локальный); `.kip/` всегда вне scan.
- **`kip rm` / `--cached`** обратимы историей; **`kip rm --purge`** — явная зачистка тел.
- **`status`** — dirty vs последнее сохранённое.
